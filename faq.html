What are USB Vendor IDs (VID) and Product IDs (PID)?

Every USB hardware device reports a 16-bit Vendor ID (VID) and a 16-bit Product ID (PID) during USB bus enumeration (for example, VID_15A2&PID_0054):

  • Vendor Identification Number (VID): Assigned exclusively by the USB Implementers Forum (USB-IF at USB.org) to uniquely identify the hardware company or OEM.
  • Product Identification Number (PID): Assigned internally by the OEM to identify the specific product model, firmware revision, or hardware variant (supporting up to 65,536 distinct product numbers per VID).

On Windows hosts, the Plug-and-Play (PnP) subsystem uses the combined Hardware ID (USB\VID_xxxx&PID_xxxx, plus interface numbers &MI_xx for composite devices) to match and load the customized Belcarra USBLAN driver.

Can Belcarra provide a Vendor ID (VID) and Product ID (PID) for our hardware?

Yes. This is a major financial and operational benefit of licensing from Belcarra.

While OEMs with their own USB-IF Vendor ID can use their assigned identifiers, hardware manufacturers are not required to purchase one. Belcarra can allocate a dedicated Product ID (PID) under Belcarra's official USB-IF Vendor ID for your device. This eliminates the substantial annual membership dues or non-member purchase fees required by USB.org, saving licensees considerable development funds and administrative effort.

How does Belcarra use VID and PID for custom driver packages?

When licensing Belcarra USBLAN, Belcarra customizes the driver INF package with either your own official VID and PID, or a dedicated PID allocated under Belcarra's Vendor ID. This guarantees seamless, conflict-free Plug-and-Play driver installation on Windows 11 (AMD64 and ARM64) and Windows 10 branded with your company and product names.

How are Belcarra USBLAN drivers tested and validated?

Belcarra executes an extensive, automated verification regimen across all supported host baselines—Windows 11 (AMD64 & ARM64) and Windows 10 (AMD64)—to ensure production stability before release:

  • Automated Cable Replug Cycling: Using Belcarra's open-source usbtestnet test harness, devices undergo repeated software disconnect/reconnect cycles via devcon to verify driver recovery, PnP adapter instantiation, and network stack re-attachment without host memory leaks or system hangs.
  • Remote Hardware Testbeds: Automated qualification pipelines leverage Raspberry Pi USB gadgets controlled via pigadget_mcp (Model Context Protocol), cycling dynamically across CDC-NCM, CDC-EEM, CDC-ECM, and RNDIS protocols.
  • Sustained Throughput & Latency: Multi-gigabyte continuous data transfers test packet aggregation, MTU boundaries, and host CPU utilization under heavy network loads.
  • Sleep, Resume & Power State Transitions: Rigorous validation across Modern Standby (S0ix) and traditional suspend/resume states ensures that network link state and IP route bindings recover immediately upon system wake.

What is an SBOM and how does Belcarra support supply chain compliance?

A Software Bill of Materials (SBOM) is a formal, machine-readable inventory of software components, dependencies, build versions, and cryptographic checksums that comprise a software release. With expanding regulatory frameworks such as the EU Cyber Resilience Act (CRA) and US Executive Order 14028 / NTIA guidelines, OEMs are increasingly required to document and track all third-party software embedded in or distributed with their products.

Belcarra delivers independent SPDX-standard SBOMs for each master driver kit and nested customer redistributable package. Each release is accompanied by cryptographic hash manifests and DigiCert-signed catalog files, allowing device manufacturers to seamlessly satisfy vulnerability management audits, supply chain security reviews, and regulatory reporting requirements.

How do I troubleshoot Device Manager error codes (Code 28, Code 10, Code 43)?

When Windows encounters an issue during USB device enumeration or driver binding, Device Manager reports a specific status code:

  • Code 28 ("Drivers for this device are not installed"): Indicates Windows Plug-and-Play (PnP) cannot find an INF matching the USB Vendor ID (VID), Product ID (PID), or composite sub-interface (&MI_xx). Ensure the hardware IDs match your custom INF package, or purge stale OEM INF files from the Driver Store.
  • Code 10 ("This device cannot start"): Indicates the driver loaded but the device firmware failed during protocol handshake or endpoint initialization on Endpoint 0 (such as SET_ETHERNET_PACKET_FILTER or GET_NTB_PARAMETERS).
  • Code 43 ("Windows has stopped this device because it has reported problems"): Indicates low-level USB bus reset timeouts, physical cable signal integrity issues, or peripheral controller (UDC) firmware crashes.

How do I remove stale driver packages from the Windows Driver Store?

When testing prototype firmware or iterating on INF configurations, Windows may cache previously installed packages in the Driver Store. To perform a clean removal:

  1. Unplug the device to prevent immediate re-enumeration.
  2. In Device Manager, right-click the network adapter, select Uninstall device, and check Attempt to remove the driver for this device.
  3. Open an elevated Command Prompt or PowerShell and inspect published packages: 
    pnputil /enum-drivers
pnputil /delete-driver oemXX.inf /uninstall /force

How can our team capture real-time driver trace logs during bring-up?

Belcarra USBLAN drivers emit real-time kernel diagnostic output using the standard Windows kernel debugging subsystem, viewable with Microsoft Sysinternals DebugView (Dbgview.exe):

  • Production driver output: Drivers in both evaluation kits and regular licensed kits are labelled Production. They emit a concise set of diagnostic messages displaying the driver version, build number, and active option settings.
  • Verbose checked/debug kits: If your engineering team needs deeper insight—including endpoint pipe transitions, CDC-NCM NTB parameters, or Endpoint 0 control request monitoring—you can request a checked/debug (chk) driver kit from Belcarra for prototype bring-up.
  • How to capture: Run DebugView as Administrator, enable Capture > Capture Kernel (Ctrl+K), and filter by USBLAN*.
